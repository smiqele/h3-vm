# Архитектура токенов

Источником истины являются JSON-файлы в `packages/ui/tokens/`. CSS-переменные для Design Lab и прототипов создаются командой `npm run tokens:generate`; ссылки между токенами проверяются через `npm run check`.

## Слои

- `core` хранит сырые шкалы: цвета, размеры, интервалы, радиусы, шрифты, высоты контролов и геометрию иконок. Компоненты не должны выбирать цвет интерфейса напрямую из этой шкалы.
- `semantic.background.app` задаёт только фон приложения. Понятие background не используется для карточек, таблиц и контролов.
- `semantic.surface` описывает непрозрачные поверхности `default`, `subtle`, `muted`, `strong`, `inverse` и `accent`. Они применяются к блокам, строкам таблицы и материалам кнопок.
- `semantic.state` хранит полупрозрачные слои hover, selected и pressed. Эти токены накладываются на поверхность и не заменяют её.
- `semantic.text` и `semantic.border` задают контрастные роли текста и границ.
- `semantic.feedback`, `status` и `visualization` разделяют сообщения, состояние ресурса и графическое представление метрик.
- `semantic.elevation` задаёт три уровня тени для всплывающих и приподнятых поверхностей.
- `components` содержит геометрию и устойчивые контракты конкретных компонентов. Компонентный токен может ссылаться на semantic, semantic — только на core.

Генератор учитывает тип токена. Все `$type: color` записываются в Light и Dark, даже если их текущие значения совпадают: это сохраняет полный цветовой контракт темы и позволяет развести значения позже без изменения структуры. Геометрия, размеры, интервалы и радиусы объявляются один раз в `:root`. Поэтому `components.button.solid.surface` и `components.button.solid.content` присутствуют в обеих темах, а `components.button.height` и `components.avatar.size.xs` не дублируются.

## Принятые решения

`Button` имеет симметричные пары `solid.{surface,content}` и `soft.{surface,content}`: solid использует `surface/accent`, soft — `surface/muted`. `SelectionControl` также называет цветовой слой `surface`, а не `background`. `DataTable`, `AppHeader`, sidebar, поля и сводки используют surface-токены. Ошибки `TextField` и `InlineAlert` используют `feedback/danger`. Меню таблицы используют `elevation/medium`.

Текстовая иерархия называется последовательно: `primary`, `secondary`, `tertiary`, `disabled`, `inverse`, `accent`. Прежняя роль `metadata` удалена: тип контента не должен определять цвет. `tertiary` используется для слабого визуального акцента и проходит AA на `surface/default` и `surface/subtle`; `disabled` зарезервирован для недоступных контролов и не считается читаемым основным текстом. `secondary` проходит AA на всех поверхностях, включая `surface/strong`.
В тёмной теме `text/primary` использует нейтральный `gray/250` (`rgb(220, 220, 220)`) вместо абсолютного белого, чтобы снизить оптическую резкость длинных текстовых поверхностей.

## Правила расширения

1. Новый цвет интерфейса сначала получает смысловую роль. Прямая ссылка компонента на `core.color` допустима только для внутренних оптических эффектов, которые вычисляются из основного semantic-цвета.
2. Новая карточка или контрол выбирает существующий surface. Новый surface добавляется только когда меняется уровень визуальной иерархии во многих компонентах.
3. Состояние ресурса не кодирует подпись внутри UI-компонента. Product model переводит API-значение в `label`, `tone` и `animated`.
4. Компонентный токен добавляется для повторяемой геометрии или публичного визуального контракта, а не для каждого CSS-свойства.
5. Новая theme-пара проходит проверку контраста до использования в компоненте.

## Следующие улучшения

- Добавить high-contrast тему после определения поддерживаемой платформы и минимальных контрастных контрактов.
- Вынести motion durations и easing в semantic motion-токены, когда появится второй компонент с тем же поведением.
- Добавить отдельные surface-роли для overlay и scrim вместе с первым Dialog или Drawer; заранее эти роли не нужны.
- Связать JSON-токены с Figma Variables после появления стабильных collection и mode identifiers.
